# 决策关键信息追问设计

日期：2026-07-31  
状态：设计已确认，待用户审核书面规范

## 1. 产品目标

Decision Council 在专家开始调研前判断用户是否缺少会显著改变结论的个人信息。如果确实缺失，系统只打断一次，以弹窗集中询问最多三个问题。用户可以回答，也可以选择“暂时不知道，继续分析”。

本功能解决以下问题：

- 专家在关键条件缺失时只能反复输出“信息不足”；
- 五位专家各自猜测用户背景，降低可信度；
- 用户已经提供过的信息仍被重复询问；
- 可由 Web Search 核实的信息被错误地交给用户回答；
- 等待用户时仍占用 Worker 或继续产生模型费用。

## 2. 已确认的产品决策

1. 采用统一“信息门槛 Agent”，不允许五位专家分别弹窗；
2. 弹窗发生在用户进入会议室后、专家正式调研前；
3. 一场会议最多弹出一次；
4. 一次最多询问三个关键问题；
5. 会议暂停等待，但用户可以选择“暂时不知道，继续分析”；
6. 用户离开会议室后，可以从首页的进行中会议卡片恢复；
7. 等待用户期间不占用 Worker，也不继续调用模型。

## 3. 方案选择

### 3.1 未采用：固定场景问卷

为买房、黄金、Offer 等场景分别配置固定问题。实现稳定，但通用性不足，容易询问用户已经回答过的信息。

### 3.2 未采用：五位专家分别提问

每位专家自行发现信息缺口。专业视角充分，但会产生重复问题、多次打断和额外模型成本。

### 3.3 采用：统一信息门槛 Agent

在决策建模后执行一次结构化判断，统一识别已有事实、关键未知、信息来源和结论影响，只生成零到三个真正需要用户回答的问题。

## 4. Agent 定位

信息门槛 Agent 是一次性结构化判定节点，不采用 ReAct，不直接调用 Web Search。

它负责判断：

- 信息是否已经由用户明确提供；
- 信息是否只能由用户本人提供；
- 信息能否交给后续 Web Search 或计算工具处理；
- 缺少该信息是否可能改变支持、反对、暂缓或有条件支持；
- 是否值得打断本场会议。

它不负责：

- 回答公开事实；
- 代替五位专家进行专业分析；
- 生成最终建议；
- 循环追问；
- 因为“知道会更好”而扩大问题数量。

## 5. 会议流程

当前用户已在创建会议前完成专家选择，因此实际图流程为：

```text
首页填写决策
→ 选择本场专家
→ 创建会议并进入会议室
→ parse_topic：决策建模
→ clarification_gate：信息门槛 Agent
   ├─ 无高影响缺失
   │   → research：五位专家调研
   └─ 有高影响缺失
       → persist_clarification：保存问题
       → 状态改为 awaiting_input
       → 本次 Worker 任务结束并释放容量
       → 用户回答或选择暂时不知道
       → clarification API 保存结果并重新入队
       → apply_clarification：合并用户信息
       → research：五位专家调研
→ 后续议会流程不变
```

不得让 Worker 使用阻塞等待的方式停在弹窗节点。

## 6. 问题生成规则

一个问题只有同时满足以下条件才允许进入弹窗：

1. 只能由用户本人提供；
2. 当前问题和背景中没有明确答案；
3. 很可能改变最终建议方向或建议强度；
4. 不能通过公开网页核实；
5. 不是仅仅“知道会更好”的辅助信息；
6. 用户可以在短时间内回答；
7. 不与其他候选问题重复。

### 6.1 优先级

按以下优先级选择最多三个问题：

1. 生存与下行风险：基本生活、应急金、负债和不可承受损失；
2. 决策目标：用户真正希望解决的问题；
3. 时间约束：决定期限、持有期、使用时间；
4. 资源约束：预算、收入、首付、可投入时间；
5. 关系与执行：配偶、家庭、合伙人和关键相关者；
6. 真实替代方案：不选择当前方案时会选择什么；
7. 不可逆条件：退出可能性和退出成本。

### 6.2 禁止问题

不得生成：

- “请详细介绍一下你的情况”；
- “你的风险偏好是什么”；
- “还有什么需要补充的吗”；
- 一句话同时询问多个独立事实；
- 需要用户自行上网或计算才能回答的问题；
- 当前输入已经明确回答的问题；
- 可以由 Web Search 获取的价格、政策、市场或公开人物信息。

## 7. 结构化数据

### 7.1 ClarificationDecision

```json
{
  "needs_clarification": true,
  "reason": "缺少两个可能改变资产配置结论的用户事实",
  "questions": [
    {
      "id": "liquid_asset_share",
      "question": "这笔投入大约占你全部可支配资金的多少？",
      "why_it_matters": "这决定价格下跌是否会影响你的基本生活和应急能力。",
      "answer_type": "single_choice",
      "options": [
        "不到20%",
        "20%–40%",
        "40%–60%",
        "60%以上",
        "不确定"
      ],
      "impact": "high",
      "source": "user_only"
    }
  ]
}
```

### 7.2 回答类型

一期只支持：

- `single_choice`：单选；
- `number`：金额、时间等数字；
- `short_text`：一句简短描述。

不支持文件上传、长问卷和多层条件分支。

### 7.3 数据库存储

为 `parliaments` 增加：

- `clarification_status`：`not_checked | not_needed | awaiting_input | answered | skipped`；
- `clarification_questions`：JSONB；
- `clarification_answers`：JSONB；
- `clarification_requested_at`；
- `clarification_answered_at`。

问题和答案必须持久化，不能只保存在前端或内存运行时。

## 8. API

### 8.1 获取会议

现有会议详情接口增加：

- `clarification_status`；
- `clarification_questions`；
- `clarification_answers`。

前端根据 `awaiting_input` 自动打开弹窗。

### 8.2 提交回答

新增：

```text
POST /api/parliament/{id}/clarification
```

请求：

```json
{
  "action": "answer",
  "answers": [
    {
      "question_id": "liquid_asset_share",
      "value": "40%–60%"
    }
  ]
}
```

跳过请求：

```json
{
  "action": "skip",
  "answers": []
}
```

接口要求：

- 校验会议所有权；
- 校验状态必须为 `awaiting_input`；
- 校验问题 ID 与回答类型；
- 使用原子条件更新保证幂等；
- 第一次成功提交后将会议重新设为 `queued`；
- 重复提交返回当前成功结果，不得重复创建任务。

## 9. 回答合并

用户回答后：

- 原始回答保存在 `clarification_answers`；
- 生成可读摘要并加入 `user_background`；
- 写入一条 `user_clarification` transcript；
- 将回答作为明确的 `user_fact` 提供给五位专家；
- 不覆盖用户此前输入，只做追加。

选择“暂时不知道”后：

- 所有未回答问题标记为 `unknown`；
- 本场永不再次弹窗；
- 专家不得擅自补全；
- 专家必须做条件分析；
- 最终总结必须展示最可能改变结论的未知条件。

## 10. 前端交互

### 10.1 弹窗

标题：

> 再补充一点，专家才能判断得更准

副文案：

> 以下问题可能直接改变会议结论。你可以回答，也可以选择暂时不知道。

每个问题展示：

- 问题序号；
- 问题正文；
- “为什么要问”；
- 对应输入控件。

底部按钮：

- 主按钮：“提交并开始会议”；
- 次按钮：“暂时不知道，继续分析”。

弹窗出现时，会议背景显示“专家尚未开始调研”，不得让用户误以为五位专家已经在等待中。

### 10.2 会议状态

新增用户可见阶段：

> 等待你补充关键信息

不展示 `interrupt`、`checkpoint`、`Worker` 等内部术语。

### 10.3 首页恢复

首页进行中会议卡片显示：

- 标签：“等待你补充”；
- 待回答问题数量；
- 按钮：“继续回答”。

点击返回会议室并自动重新打开弹窗。

### 10.4 跳过提示

用户跳过后，在讨论流显示：

> 已按未知条件继续。专家会分别说明不同条件下结论如何变化。

## 11. Worker 与生命周期

`awaiting_input` 是有效的非终态，但不属于 `running` 或 `queued`。

要求：

- Worker 只领取 `queued` 会议；
- 信息门槛生成问题后将状态改为 `awaiting_input` 并结束当前任务；
- `awaiting_input` 不计入 Worker 活跃任务数；
- 提交或跳过后重新进入 `queued`；
- 首页 heartbeat 可以保持会议入口，但等待输入不依赖 heartbeat 存活；
- 当前“用户离站后取消会议”的扫描必须排除 `awaiting_input`；
- 当前“回收超时 running 任务”的逻辑不得把 `awaiting_input` 标成失败；
- 用户主动结束会议时可以从 `awaiting_input` 进入 `cancelled`。

## 12. SSE 与事件

新增事件：

- `clarification_requested`；
- `clarification_answered`；
- `clarification_skipped`；
- `clarification_resumed`。

`clarification_requested` 只包含用户可见问题，不包含模型原始推理。

SSE 断开或页面刷新不影响问题状态；页面重新加载时以数据库会议详情为准。

## 13. 异常处理

- Agent 调用失败：标记 `not_needed`，直接进入专家调研；
- 输出超过三个问题：按影响排序保留前三个；
- 输出空泛、重复或可由 Web 获取的问题：规则校验删除；
- 校验后没有问题：标记 `not_needed`，直接调研；
- 数据库存储问题失败：不进入等待状态，记录错误并继续调研；
- 用户提交网络失败：保留弹窗输入并允许重试；
- 两个页面同时提交：只接受第一次原子更新；
- 用户刷新或离开：回来后恢复；
- 用户跳过：不允许再次触发；
- 用户主动结束：正常取消会议。

## 14. 最终总结

回答过的问题进入“用户信息”依据。

跳过的问题进入：

- 尚未解决的关键条件；
- 结论翻转条件；
- 下一步建议。

最终总结页不展示信息门槛 Agent 的内部工作路径，只展示用户问题、用户答案或明确的未知状态。

## 15. 测试与验收

### 15.1 单元测试

- 已有事实不被重复询问；
- Web Search 可回答的问题不询问用户；
- 最多三个问题；
- 空泛和重复问题被删除；
- 跳过后不再触发；
- 回答正确合并为用户事实；
- 信息门槛失败时正常降级。

### 15.2 API 测试

- 正确提交回答；
- 正确跳过；
- 非等待状态拒绝提交；
- 无效 question ID 被拒绝；
- 重复提交保持幂等；
- 设备所有权生效。

### 15.3 Worker 测试

- `awaiting_input` 不被领取；
- 进入等待后释放并发容量；
- 回答后重新排队；
- 离站扫描不取消等待输入的会议；
- Worker 重启后问题仍可恢复。

### 15.4 前端测试

- 收到等待状态自动弹窗；
- 刷新后恢复；
- 首页正确展示“等待你补充”；
- 提交后关闭弹窗并显示重新排队状态；
- 网络失败保留用户已填写内容；
- 移动端可完整填写和操作。

### 15.5 成功标准

- 一场会议最多弹出一次；
- 问题数不超过三个；
- 用户回答后五位专家都能使用答案；
- 用户跳过后最终结论保留条件；
- 等待用户期间模型调用数为零；
- 等待用户期间 Worker 占用为零；
- 刷新、返回首页和 Worker 重启均不丢失问题。

## 16. 非目标

- 不做持续多轮追问；
- 不让五位专家分别询问用户；
- 不把首页改成长问卷；
- 不使用弹窗询问公开事实；
- 不让信息门槛 Agent 给出最终建议；
- 不在一期支持附件和复杂表单；
- 不改变现有两到三轮议会讨论结构。
