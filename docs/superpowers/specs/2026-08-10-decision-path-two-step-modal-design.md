# 决策路径两步式弹窗设计

日期：2026-08-10
状态：已确认，待实施

## 1. 背景

当前 `DecisionPathModal` 在同一个滚动弹窗中同时展示任务简报、比较方案、分析重点、研究说明、最终交付、简报确认、事实校正和关键问题。首屏信息层级过多，用户需要先阅读一份长简报，才知道如何继续；底部主按钮又会在前置条件未满足时保持禁用，容易产生“页面卡住”的感觉。

本次改版将弹窗重构为两步式聚焦向导，并采用“深墨决策台”视觉语言。目标是降低认知负担、明确每一步的目的，同时保留现有决策路径生成、修订和会议创建能力。

## 2. 目标与非目标

### 2.1 目标

- 将“确认任务”和“补充信息”拆成两个清晰步骤。
- 第一步让用户在数秒内判断系统是否正确理解了决策任务。
- 第二步一次只展示一个关键问题，并持续反馈完成进度。
- 允许用户明确回答“不确定”，避免因为信息缺失被流程卡住。
- 在桌面端和移动端都保持清晰、紧凑、可操作。
- 网络失败或重新生成时保留用户已经填写的内容。

### 2.2 非目标

- 不修改后端接口、数据库结构或决策路径数据模型。
- 不改变问题生成算法、专家选择逻辑或会议执行流程。
- 不在本次改版中重做议会页面的整体视觉系统。
- 不增加新的分析内容或新的必填字段。

## 3. 设计方向

### 3.1 交互方案

采用“聚焦式两步向导”：

1. `确认任务`：展示压缩后的任务理解，让用户确认或请求修订。
2. `补充信息`：逐题收集会明显影响结论的信息，最后创建会议。

弹窗顶部始终展示两步进度：`1 确认任务 — 2 补充信息`。当前步骤使用深墨蓝实心标识，未到达步骤使用低对比度灰蓝标识。

### 3.2 视觉语言

采用“深墨决策台”方向：

- 主色为深墨蓝 `#172D4D`，用于主按钮、当前步骤和选中态。
- 页面使用冷白背景、浅灰蓝边界和深灰正文，减少现有紫色、金色、泛黄底色之间的竞争。
- 弹窗桌面端最大宽度为 560px；移动端左右各保留 12px 安全间距，并确保操作区始终容易触达。
- 阴影克制，边框轻薄；视觉重点来自层级、间距和排版，而不是装饰性容器。
- 决策目标使用左侧细色条的信息块；比较方案使用低对比度胶囊标签。

## 4. 用户流程

### 4.1 打开与生成

用户在首页发起讨论后打开弹窗。系统生成决策路径期间显示统一加载状态和文案“正在梳理本次决策任务…”。生成成功后进入第一步；生成失败时展示错误信息和“重新生成”按钮，同时保留弹窗和原始输入上下文。

### 4.2 第一步：确认任务

第一步只展示：

- 一句决策目标；
- 最多三个主要比较方案；
- 一条“重点分析”摘要；
- 一条“最终交付”摘要。

不在首屏展开完整交付清单、研究政策说明、已识别事实或关键问题。

主要操作为“理解正确，继续”。次要操作为“返回修改决策”。“这个理解不准确？”作为轻量文本操作，展开后显示反馈输入框和“根据补充重新生成”按钮。

修订成功后仍停留在第一步，展示新简报并要求用户重新确认。问题 ID 稳定时继续保留已有答案；不存在于新结果中的答案按当前逻辑移除。

### 4.3 第二步：补充信息

第二步一次展示一个问题，并包含：

- 当前进度，例如 `问题 2 / 4`；
- 问题正文；
- `why_it_matters` 或对应解释文案；
- 当前问题的输入控件；
- “上一步”和主操作；
- “暂时不知道，交给专家判断”。

单选题点击选项后保留 200ms 选中反馈，再进入下一题；最后一题不自动创建会议，而是显示“确认并召开会议”供用户明确确认。多选题和文本/数字题使用“继续”按钮提交当前答案。

用户可以返回上一题修改答案。返回第一步时不丢失任何已答内容。

### 4.4 不确定答案

“暂时不知道，交给专家判断”是合法答案，不是空值或未完成状态。界面使用这句中文文案；状态与请求继续使用后端已有的协议值 `unknown`，并随现有 `decision_path_answers` 请求提交。

因此：

- 该题视为已回答；
- 用户可以继续到下一题或创建会议；
- 专家能在会议上下文中识别该信息仍需核实；
- 不需要修改后端当前的完整性判断。

## 5. 组件边界

现有组件拆分为三个职责明确的单元：

### 5.1 `DecisionPathModal`

负责：

- 生成、修订和删除决策路径草稿；
- 保存当前步骤、答案、错误和提交状态；
- 调用会议创建接口；
- 协调两个步骤之间的导航；
- 处理打开、关闭和重置生命周期。

### 5.2 `TaskConfirmationStep`

负责：

- 展示压缩后的任务简报；
- 展示“理解正确”“返回修改”和“理解不准确”入口；
- 收集简报反馈并触发重新生成；
- 展示生成或修订失败状态。

它不直接调用 API，只通过属性接收数据和回调。

### 5.3 `DecisionQuestionsStep`

负责：

- 根据当前问题索引展示单题；
- 渲染单选、多选、文本和数字输入；
- 展示进度与问题解释；
- 处理上一题、下一题、不确定答案和最终确认；
- 确保窄屏下操作区可用。

它不负责创建会议，只在最后一题完成时调用父组件提供的确认回调。

## 6. 状态与数据流

弹窗内部增加界面步骤状态：

- `confirm_task`
- `answer_questions`

现有请求状态 `generating`、`revising`、`ready`、`creating_meeting` 和 `create_failed` 保持不变。界面步骤与请求状态分开管理，避免用一个枚举同时表达“用户在哪一步”和“网络请求在做什么”。

答案继续保存为 `Record<string, string | string[]>`。当前问题位置保存为数值索引，并在预览结果改变时约束在有效范围内。

现有 `factEdits` 和 `editingFactId` 只改变本地展示，未进入会议创建请求。新流程不再展示“已识别事实”的独立编辑区，并删除这两个无效的本地状态；后端生成的事实仍随决策路径草稿保留，不改变服务端行为。

创建会议时继续使用现有参数：

- `decision_path_generation_id`
- `brief_confirmation: "confirmed"`
- `decision_path_answers`
- 现有主题、分类、背景、专家和幂等键字段

本次改版不新增接口字段。

## 7. 错误与边界状态

- 初次生成失败：停留在弹窗内，显示原因和“重新生成”。
- 简报修订失败：保留原简报、反馈文字和已有答案，允许重试。
- 创建会议失败：保留当前问题位置和全部答案；主按钮变为“重试创建会议”。
- 没有关键问题：第一步确认后直接进入最终确认并创建会议，不显示空的第二步。
- 仅有一个问题：进度显示 `问题 1 / 1`，回答后直接显示“确认并召开会议”。
- 关闭弹窗：沿用现有行为，将当前草稿标记为过期，再返回首页编辑。
- 遮罩点击：仍不关闭弹窗，避免误丢失内容。
- 键盘与辅助技术：弹窗保留 `role="dialog"`、`aria-modal` 和标题关联；切题后焦点移动到新问题标题；所有选项和操作均可通过键盘完成。

## 8. 响应式规则

- 桌面端弹窗最大宽度为 560px，最大高度不超过视口，内容区独立滚动。
- 移动端弹窗接近全屏高度，顶部进度和底部操作区固定，中间问题区滚动。
- 触控选项最小高度 44px。
- 文本不得仅依靠颜色表达当前步骤、选中、失败或禁用状态。
- 主操作在可执行时始终为高对比度深墨蓝；不可执行时同时提供原因或明确的下一步提示。

## 9. 验收标准

### 9.1 功能

- 成功生成后默认展示第一步，不展示关键问题长列表。
- 点击“理解正确，继续”后进入逐题界面。
- 用户能前后切换问题，答案不会丢失。
- 单选、多选、文本和数字题均能正确保存答案。
- 点击“不确定”后该题被视为已回答，并提交明确答案值。
- 最后一题完成后能够创建会议，请求字段与改版前兼容。
- 修订、生成和创建失败时均能重试，且保留已有输入。
- 零问题和单问题场景行为符合第 7 节定义。

### 9.2 视觉与可用性

- 1440px 桌面视口下，第一步无需滚动即可看到核心内容和主操作。
- 375px 宽移动视口下，不出现横向滚动，底部主操作始终可触达。
- 当前步骤、问题进度、选中答案和错误状态均清晰可辨。
- 用户不会因灰色按钮而无法判断下一步需要完成什么。

### 9.3 测试

- 使用 Vitest、React Testing Library 和 `jsdom` 建立轻量前端组件测试环境。
- 为两步导航和答案保留添加组件测试。
- 覆盖简报修订、问题前后切换、不确定答案和失败重试。
- 验证最终创建请求 payload。
- 执行 TypeScript 类型检查和 Next.js 生产构建。
- 对桌面端与移动端进行视觉检查，确认滚动、固定操作区和长文案表现。
