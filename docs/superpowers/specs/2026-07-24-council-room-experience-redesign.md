# 斜杠二级会议体验改版设计

日期：2026-07-24

状态：已确认，待实施计划

范围：专家选择页、会议进行页、会议实时状态、议会工作流收敛

## 1. 背景

当前会议页已经接入数学家、经济学家、心理学家等职业专家和局部自治 Agent，但用户体验仍存在明显问题：

- 首页提交后直接进入会议室，用户不知道为何选择这些专家，也无法调整。
- 专家名单返回前页面只显示 `0/5`，排队或分析较慢时看起来像没有反应。
- 会议页沿用旧版深色议会视觉，与新版米色首页和朋友版原型不一致。
- Agent 调研轨迹占据较高视觉权重，人物观点与讨论氛围反而不突出。
- 当前多轮全员辩论调用量大、耗时长，旧任务容易堵塞新会议。
- 取消只能在大节点之间生效；排队、断线、部分失败和提前总结缺少完整产品状态。

本次改版采用“朋友版外壳 + 真实 Agent 议会”：视觉与主要交互尽量继承朋友版本，同时保留并强化真实 Agent 的自主调研、工具调用、证据和可恢复运行状态。

## 2. 设计目标

1. 让用户在会议开始前理解并控制专家构成。
2. 进入会议室后立即给出明确反馈，任何时刻都能回答“正在发生什么”。
3. 保留朋友版鲜活、直观的多人聊天室体验。
4. 以行动摘要展示 Agent 能力，不展示内部思维链。
5. 将正常会议目标耗时控制在 2–3 分钟。
6. 单个专家或单次工具失败不能拖垮整场会议。
7. 页面刷新、实时连接中断后可以从服务端快照恢复。

## 3. 非目标

- 一期不支持创建自定义讨论者。
- 会议开始后不支持直接增删专家。
- 不展示模型的隐藏推理或逐字思维链。
- 不在本次改版中加入商业化、支付、套餐或额度购买。
- 不增加新的职业专家；一期仍使用现有六位内置专家。

## 4. 方案比较与选择

### 方案 A：高度复刻朋友版

完整继承四栏聊天室、人物列表和持续对话体验。人物感强，但真实 Agent 调研与证据过程容易被隐藏。

### 方案 B：决策分析工作台

减少装饰栏，突出专家结论、证据和进度。信息效率最高，但更像专业工具，产品趣味性和人物感较弱。

### 方案 C：朋友版外壳 + 真实 Agent 议会

保留朋友版四栏聊天室、人物状态和输入体验，同时加入阶段进度、Agent 行动摘要、证据展开和主席总结。

**最终选择：方案 C。**

## 5. 完整用户动线

页面路径：

`首页 → /council/setup → /parliament/{id} → /summary/{id}`

### 5.1 首页提交

用户在首页选择精选场景并填写决策背景，或直接填写通用问题。

提交后先进入专家选择页，不立即创建会议，也不启动正式分析。

### 5.2 选择讨论者

选择页左侧展示本次议题、关键背景摘要和推荐逻辑，右侧展示六位内置专家。

系统根据议题默认勾选五位专家。每张被推荐的卡片显示：

- 专家名称与职业形象。
- 该专家的分析方法。
- 针对当前问题的一句话推荐原因。
- 已选择状态。

用户可以取消、补选或更换专家：

- 最少选择 3 位。
- 最多选择 5 位。
- 默认选择 5 位。
- 不展示“创建新讨论者”。

点击“开始讨论”后，才把用户最终选择的专家提交给后端并创建正式会议。

### 5.3 进入会议室

会议室立即使用创建请求中的专家名单渲染专家席，不等待工作进程再次返回名单。

用户第一屏必须看到：

- 当前议题。
- 已选择的全部专家。
- 当前会议阶段。
- 明确的运行状态。
- 可补充背景的输入框。

不允许再出现名单为空但显示 `0/5` 的无解释状态。

### 5.4 讨论过程

会议采用四阶段：

1. 理解问题。
2. 自主调研。
3. 观点交锋。
4. 主席总结。

用户可以随时：

- 补充背景。
- `@` 某位专家追问。
- 叫停会议。
- 在满足条件后请主席提前总结。
- 查看专家和 Agent 行动详情。

会议开始后，“编辑参与者”改为“查看专家”。如果用户要更换专家，需要结束当前会议，并基于原问题重新发起一场。

### 5.5 进入纪要

正常完成或提前总结后进入独立纪要页。部分成功的会议也生成部分纪要，并明确哪些专家或阶段未完成。

## 6. 视觉与布局

### 6.1 视觉语言

继承朋友版视觉变量：

- 页面底色：米白 `#fffaf6`。
- 内容表面：白色或浅米色 `#fffdfb`。
- 主文字：深紫黑 `#251536`。
- 主按钮：梅紫渐变 `#30103f → #4b1c62`。
- 强调色：珊瑚红 `#ec403d`。
- 分割线：暖灰 `#e9ded8`。
- 卡片圆角、轻阴影和克制动效与朋友版保持一致。

### 6.2 专家选择页

顶部采用三列结构：

- 左侧：返回修改问题。
- 中间：斜杠 Logo。
- 右侧：`02 / 选择讨论者`。

主体采用左右分栏：

- 左栏：议题、背景摘要、系统推荐逻辑。
- 右栏：六位专家卡片和固定底部操作条。

桌面端专家卡片两列，移动端单列。固定操作条显示已选择人数和“开始讨论”按钮。

### 6.3 会议进行页

桌面端沿用朋友版四栏：

1. 窄导航栏：品牌标记、当前会议、返回。
2. 会话栏：本次议会、专家数量、当前阶段和用户操作提示。
3. 聊天主区：标题、阶段条、议题、时间线、输入区。
4. 专家席：专家状态与折叠的 Agent 实况说明。

聊天主区的信息优先级为：

1. 专家观点。
2. 用户补充。
3. 阶段与系统反馈。
4. Agent 行动摘要。
5. 展开后的工具和证据详情。

### 6.4 移动端

小于 900px 时：

- 隐藏会话栏和右侧专家栏。
- 保留窄导航栏和聊天主区。
- 专家席变为聊天区顶部横向头像条。
- 阶段条保持四段，但使用短标题。
- 底部输入区固定且无横向溢出。
- “叫停”和“请主席总结”收入更多操作菜单，发送按钮保持可见。

## 7. 会议阶段与讨论节奏

### 7.1 理解问题

主持人从议题和背景中提炼：

- 用户目标。
- 关键约束。
- 需要比较的主要选项。
- 信息缺口。

该阶段结束后发布一条可见的主持人消息，让用户确认议会理解的问题。

### 7.2 自主调研

最终选择的 3–5 位专家并行执行一次局部自治 Agent 调研。

每位专家可以基于自身角色决定是否使用被允许的工具，但仍受现有 Harness 约束：

- 工具白名单。
- 调用次数上限。
- 单次请求超时。
- 总运行时间上限。
- 查询脱敏。
- 证据账本。
- 公开安全轨迹。

主时间线只显示公开行动摘要，例如：

> 经济学家正在搜索当地房贷利率和租售比。

展开后显示工具名称、脱敏查询、来源预览和证据，不显示隐藏推理。

### 7.3 观点交锋

所有可用初步观点形成后，系统确定观点差异最大的三位专家，进行一次交叉回应。

差异选择应优先考虑：

- 支持、反对或条件性建议的方向差异。
- 采用的方法差异。
- 关键变量或风险判断差异。
- 非降级结果优先。

不再运行三轮全员重复辩论。

### 7.4 主席总结

主席综合：

- 当前共识。
- 核心分歧。
- 证据强弱。
- 哪些条件会让结论反转。
- 风险边界。
- 推荐的下一步行动。

主席选择和输入材料必须可由服务端状态重建。

## 8. 用户插话与控制

### 8.1 用户补充

用户消息先乐观显示，再发送给后端。后端确认后追加系统反馈：

> 已收到，这条信息将影响接下来的专家判断。

应用规则：

- 调研阶段：应用到尚未完成的专家与后续交锋。
- 交锋阶段：应用到下一位发言者与主席总结。
- 总结阶段：不静默重跑，提示用户在纪要后发起补充追问。

如果后端接收失败，用户消息明确标记“未应用”，并提供重试。

### 8.2 提前总结

至少有三位专家形成初步观点后，“请主席总结”才可用。

触发后：

- 不再开启新的工具调用。
- 等待当前短任务结束或超时。
- 使用已有观点和证据生成总结。
- 纪要标注“提前总结”以及未完成专家。

### 8.3 叫停

叫停需要二次确认。确认后：

- 后端立即记录取消请求。
- 当前工具或模型调用在独立超时内终止。
- 不再进入新阶段。
- 使用已有内容生成可查看的部分结果，或保留当前时间线。

## 9. 默认专家推荐

首页提交后调用轻量推荐接口：

`POST /api/expert-selection/preview`

建议请求：

```json
{
  "topic": "现在买房，还是再等一年？",
  "topic_category": "real_estate",
  "user_background": "预算 300 万，自住，计划持有 8 年"
}
```

建议响应：

```json
{
  "recommended_expert_ids": [
    "mathematician",
    "economist",
    "psychologist",
    "historian",
    "politician"
  ],
  "coverage": ["现金流", "机会成本", "居住需要", "周期", "利益相关者"],
  "reasons": {
    "mathematician": "比较预算、月供和持有期限",
    "economist": "分析机会成本和替代收益"
  }
}
```

规则：

- 固定场景优先使用确定性映射，保证快速、稳定和可测试。
- 通用议题使用一次轻量分类。
- 推荐失败时采用稳定的默认五人组合，并提示用户可调整。
- 推荐接口不创建会议，不执行专家调研。

创建会议请求新增 `selected_expert_ids`。后端验证数量、合法 ID 和去重后，以用户最终选择为准，不再在工作进程中覆盖。

## 10. 前端组件边界

### `CouncilSetup`

负责加载推荐、管理用户选择和提交最终专家。依赖推荐接口与创建会议接口。

### `ExpertSelectionCard`

只负责展示专家、推荐理由和选择状态，不包含网络逻辑。

### `CouncilRoom`

负责加载会议快照、订阅实时事件、合并状态并组织四栏布局。

### `CouncilPhaseBar`

根据服务端阶段渲染进度，不自行推断后端流程。

### `ExpertSeatPanel`

展示选中专家、状态和当前活动；点击打开专家详情。

### `CouncilTimeline`

按服务端序列号合并专家观点、用户消息、系统状态和 Agent 行动，负责去重和稳定排序。

### `CouncilComposer`

负责补充背景、`@` 专家、叫停和提前总结的交互与可用条件。

### `AgentActionDetail`

展示安全轨迹、工具、来源和证据，不渲染隐藏思维链。

组件之间通过明确属性和事件通信，避免继续扩大当前单文件会议页。

## 11. 服务端状态与事件协议

### 11.1 持久化快照

会议快照至少包含：

- 会议状态。
- 当前阶段。
- 最终选择的专家 ID。
- 每位专家的状态。
- 时间线事件。
- Agent 公开行动。
- 用户补充及是否已应用。
- 可用专家结果。
- 是否为提前总结或部分结果。

页面首次进入、刷新或实时连接重连时，先加载快照，再从最后事件序号续订。

### 11.2 产品事件

稳定事件类型：

- `council_queued`
- `council_started`
- `phase_changed`
- `expert_started`
- `expert_action`
- `expert_opinion`
- `expert_failed`
- `user_context_applied`
- `chair_summary_started`
- `council_completed`
- `council_partial`
- `council_cancelled`

每个事件包含：

- 单调递增的 `seq`。
- `parliament_id`。
- 事件时间。
- 可公开 payload。

前端不再依赖具体 LangGraph 节点名称决定产品展示；服务端负责把内部节点翻译为稳定产品事件。

## 12. 异常与恢复

### 12.1 排队

资源繁忙时显示：

> 五位专家已入席，正在等待空闲分析席位。

显示已等待时长，不提供无法保证的预计时间。用户可以离开页面，稍后通过会议链接回来。

### 12.2 单个专家失败

- 状态显示“信息有限”或“本轮未完成”。
- 其他专家继续。
- 最终纪要注明缺失视角。
- 提供单专家手动重试入口；不自动重复调用。

### 12.3 实时连接断开

- 顶部显示“正在恢复连接”。
- 使用指数退避自动重连。
- 已显示消息不清空。
- 重连后从最后 `seq` 补齐事件。
- 多次失败后允许用户手动刷新快照。

### 12.4 超时

- 每个模型与工具调用独立超时。
- 每个工作流阶段之间检查取消。
- 整场达到硬超时后生成部分纪要，而不是只显示错误。
- 部分纪要明确已完成和未完成范围。

### 12.5 推荐失败或创建失败

- 推荐失败：使用默认五人组合，选择页仍可用。
- 创建失败：保留用户的议题、背景和选择，允许原地重试。
- 禁止重复点击创建多场相同会议。

## 13. 安全、隐私与可访问性

- Agent 轨迹继续执行查询脱敏和来源清理。
- 匿名用户不可调用跨会议记忆。
- 用户背景不出现在不必要的公开工具查询中。
- 不向用户展示隐藏思维链。
- 所有按钮支持键盘操作和清晰焦点态。
- 状态不仅依赖颜色，同时提供文字和图标。
- 动效遵循 `prefers-reduced-motion`。
- 移动端触控目标不小于 44px。

## 14. 验收标准

### 14.1 核心体验

- 首页提交后 1 秒内进入选择页或显示明确加载状态。
- 默认推荐五位专家，用户可调整为 3–5 位。
- 创建会议使用用户最终选择，后端不覆盖。
- 进入会议室立即显示全部已选专家和当前阶段。
- 排队、断线、超时、单专家失败均有明确反馈和下一步操作。
- 用户补充立即显示，并能确认是否被后续流程采用。
- 至少三位专家完成后可以提前总结。
- 正常会议目标耗时 2–3 分钟。

### 14.2 视觉与响应式

- 桌面端实现朋友版四栏会议布局。
- 首页、选择页、会议页共享米白与梅紫视觉语言。
- 手机端无横向溢出。
- 手机端可完成选择、查看进度、补充信息、提前总结和叫停。

### 14.3 自动化测试

覆盖：

- 固定场景确定性推荐。
- 通用议题推荐回退。
- 3–5 位选择验证。
- 创建请求采用最终专家。
- 产品事件映射与序号去重。
- 页面刷新和断线恢复。
- 用户补充成功、失败和重试。
- 提前总结条件与部分结果。
- 取消在阶段边界和调用超时内生效。
- 单专家失败不阻塞会议。

### 14.4 真实体验测试

使用 20 个覆盖职业、房产、投资、创业、关系与通用决策的真实案例运行完整会议。

发布门槛：

- 完成率不低于 95%。
- P95 总耗时不高于 180 秒。
- 不发生用户隐私泄露。
- 断线重连后无重复消息或缺失消息。
- 单专家失败时仍能生成可用纪要。
- 单场调用成本不超过预设上限。

## 15. 实施顺序

1. 增加推荐预览接口与最终专家选择参数。
2. 新建专家选择页并接入首页。
3. 建立稳定产品事件与可恢复会议快照。
4. 收敛后端工作流与取消/部分结果行为。
5. 重构会议页为四栏组件结构。
6. 接入用户补充、提前总结和异常状态。
7. 完成移动端与可访问性。
8. 自动化测试、真实模型验证和 20 案例发布测试。

## 16. 成功定义

用户进入会议后，不需要理解技术架构，也能感知到：

- 五位不同的人正在认真处理我的问题。
- 我知道他们现在在做什么。
- 我可以参与并改变讨论。
- 他们的判断有真实资料和方法支撑。
- 即使某一步失败，我仍能得到一个可用结果。

同时，产品能够自然展示开发者对多 Agent 工作流、局部自治 Agent、工具调用、Harness、安全轨迹、流式状态和故障恢复的理解。
